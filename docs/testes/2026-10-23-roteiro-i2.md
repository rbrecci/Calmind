# Roteiro I2 em 23/10/2026: demonstração cruzada do RNF-61 (segunda execução)

Critério (etapa I2, seção 5 de [etapas-sprint2.md](../planejamento/etapas-sprint2.md)): o admin aprova um psicólogo no painel web e ele aparece no app, na mesma sessão.

**Resultado em uma frase:** o critério foi comprovado de ponta a ponta no Expo web: a Jane Marple não aparecia no catálogo do app, foi aprovada pelo clique real no painel admin, teve o perfil publicado e passou a aparecer no catálogo do Frodo (nome, CRP 06/000003, abordagem e modalidade, sem preço, nota, estrela nem ranking), sem reiniciar nada. O app só a mostrou depois das três condições (documento, aprovação e perfil publicado); a aprovação sozinha não bastou.

Histórico: a primeira execução do dia, feita quando o app ainda não tinha tela de catálogo, não conseguiu mostrar o psicólogo no app (capturas [01](capturas-i2/2026-10-23-01-painel-admin-antes-jane-pendente.png) a [04](capturas-i2/2026-10-23-04-app-web-paciente-home-sem-catalogo.png), mantidas no disco). Este documento a substitui.

- API Laravel em `http://localhost:8000` (`/admin/login` respondeu 200), banco `calmind` recém recriado com `migrate:fresh --seed`.
- Expo web em `http://localhost:8082`, subido só para esta execução, com as variáveis passadas no comando (sem editar o `app/.env`): `EXPO_PUBLIC_USE_MOCK=false` e `EXPO_PUBLIC_API_URL=http://localhost:8000/api/v1`. A porta 8081 já estava ocupada por outro Expo com o IP da LAN e não foi usada nem alterada. O servidor da 8082 foi encerrado no fim.
- Contas fictícias do seeder: ver `backend/database/seeders/UserSeeder.php` (admin, paciente Frodo Bolseiro, psicóloga pendente Jane Marple, sem documento). Tokens não aparecem aqui.

## Preparo da demonstração

A Jane do seed não tem documento, então o painel recusa aprovar. Quem for apresentar prepara a Jane como a própria profissional, pela API, e deixa a aprovação e a publicação para a hora da apresentação. Ordem usada nesta execução:

1. Subir o app (em `app/`, sem editar o `.env`):
   `EXPO_PUBLIC_USE_MOCK=false EXPO_PUBLIC_API_URL=http://localhost:8000/api/v1 npx expo start --web --port 8082`
2. Antes da apresentação (documento): login da Jane e envio do comprovante, em Git Bash na raiz do repo (senha: ver `UserSeeder`):
   ```bash
   A=http://localhost:8000/api/v1
   curl -s -X POST $A/auth/login -H "Accept: application/json" -H "Content-Type: application/json" \
     -d '{"email":"jane.marple@example.com","password":"<senha da Jane, ver UserSeeder>"}'
   # a resposta traz {"token":"..."}; guarde em TOKEN (nao imprima nem grave)
   curl -s -X POST $A/psychologist/registration -H "Accept: application/json" -H "Authorization: Bearer $TOKEN" \
     -F crp_region=06 -F crp_number=000003 -F "document=@docs/api/fixtures/comprovante-teste.pdf;type=application/pdf"
   ```
3. Na apresentação, no painel `http://localhost:8000/admin/login` (conta admin: ver `UserSeeder`): clicar em "Aprovar Jane Marple". Mostrar o catálogo do Frodo no app: a Jane ainda não aparece.
4. Perfil e publicação, como Jane:
   ```bash
   curl -s -X PUT $A/psychologist/profile -H "Accept: application/json" -H "Content-Type: application/json" \
     -H "Authorization: Bearer $TOKEN" --data-binary @perfil.json
   curl -s -X POST $A/psychologist/profile/publish -H "Accept: application/json" -H "Authorization: Bearer $TOKEN"
   ```
   com `perfil.json` contendo `profile_approach` "Terapia humanista", `profile_specialty` "Ansiedade e autoconhecimento", `profile_modality` "online", `profile_region` e `profile_bio` "Terapia humanista para adultos. Atendimento online.".
5. No app, como Frodo: Voltar e "Encontrar profissional" de novo. A Jane aparece.

Armadilhas encontradas:

- No `PUT` do perfil, texto com acento passado direto em `-d '...'` no Git Bash não gravou nada (HTTP 200, campos `null`). O que funcionou foi arquivo JSON com `ã` escapado e `--data-binary @arquivo`. Nesse caso o publish recusou com HTTP 422 ("Escreva uma apresentação antes de publicar."), porque a bio não tinha sido gravada.
- O catálogo exige as três condições em qualquer ordem (documento e aprovação, mais perfil publicado), mas a aprovação só é possível com documento.

## O que o roteiro mostra

1. Painel web, API e app leem o mesmo banco: a aprovação feita por clique na interface Blade e a publicação do perfil mudaram o que o app do paciente exibe, sem reiniciar nada e na mesma sessão do app.
2. Para um psicólogo aparecer no catálogo do app são três condições, não uma: documento enviado, cadastro aprovado pelo admin e perfil publicado pelo próprio psicólogo. Os passos 5', 4b' e 6' mostram que as duas primeiras sozinhas não bastam.
3. O painel recusa aprovar cadastro sem documento (passo 3), conforme o RF-44.
4. O catálogo do app não exibe preço, nota, estrela nem ranking (passo 6').

## Limites (o que não foi comprovado)

- Só Expo web, no navegador. Não foi testado em celular físico, nem em emulador Android ou iOS (o armazenamento do token difere na web, ver README do app).
- O preparo da Jane exige a API (curl): o app ainda não tem fluxo de cadastro profissional (F2 e F3 ficaram fora). Portanto "o psicólogo se cadastra e é aprovado" não foi demonstrado pelo app, só "aprovado no painel aparece no app".
- A aprovação não foi feita sobre o estado puro do seed (a Jane do seed não tem documento). Dados alterados além da aprovação: documento anexado, perfil preenchido e publicado, tudo pela API autenticada como a própria Jane.
- O banco foi recriado antes desta execução e será recriado de novo depois dela; os dados acima não persistem.
- O app foi apontado para `localhost:8000` por variável de ambiente, diferente do `app/.env` (IP da LAN). O comportamento com o IP da LAN no `.env` não foi reexecutado.
- Tokens de login não foram gravados neste arquivo. Senhas e e-mail do admin: ver `UserSeeder`.
- Não foi verificado se a Jane aparece em telas de outros papéis; o escopo foi admin e paciente.
